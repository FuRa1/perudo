## 2. ОБЗОР ПРОЕКТА

Сетевая (не хотсит) игра Перудо (Liar's Dice / Dudo) на **2–12 игроков**, тема «Пираты Карибского моря». Каждый игрок подключается со своего устройства. Цель MVP — полный играбельный цикл партии от создания комнаты до определения победителя. Без глубокого визуального полиша, без ботов, без OAuth, без видео.

**Три фундаментальных принципа:**
1. **Сервер — единственный источник истины.** Клиент отправляет только *намерения* (intents) и отображает состояние с сервера. Клиент не вычисляет исход и не владеет случайностью или таймерами.
2. **Доменная логика изолирована от транспорта.** `GameEngine` не знает про Socket.io, HTTP, Angular — запускается и тестируется в вакууме.
3. **Данные, а не хардкод.** Все игровые константы, структура костей, тексты — в одном месте, не магическими числами по коду.

## 3. АРХИТЕКТУРА И СТЕК

### 3.1 Монорепозиторий
```
/perudo-game
  /client    → Angular 21 (standalone components + Signals) + Ionic 9 + Tailwind CSS
             → Capacitor: веб + Android + iOS из одной кодовой базы
  /server    → NestJS + Socket.io (@WebSocketGateway) — авторитетная игровая логика
  /shared    → общие TS-типы, enum'ы фаз, константы правил, ЧИСТЫЕ функции (валидация/сравнение ставок)
```

### 3.2 Роль каждого пакета

**`/shared` — контракт между клиентом и сервером.** Здесь:
- Все TS-типы игрового состояния и событий (интерфейсы intent'ов и серверных сообщений).
- Enum фаз игры (машина состояний, 6.1).
- Единый конфиг правил-констант (3.4).
- **Чистые функции** без побочных эффектов: валидация легальности ставки, сравнение ставок по шкале с конверсией единиц (5.4), подсчёт фактического количества с учётом джокеров.
- Эти функции импортируются **и клиентом, и сервером**: сервер применяет их авторитетно, клиент — для мгновенной предвалидации UI и подсказок (5.8). Пишем один раз, без дублирования логики.

**`/server`** — оркестрация: держит состояние комнат, применяет intent'ы через `GameEngine`, управляет таймерами, рассылает отфильтрованное состояние. Socket.io-слой тонкий.

**`/client`** — презентация: компоненты читают состояние из единого стора (Signals), шлют intent'ы через сервисный слой. **Компоненты не общаются с Socket.io напрямую** — только через сервис-обёртку.

### 3.3 Модель состояния и хранение
- Состояние партий — **в памяти сервера** (Map по roomId). При рестарте активные партии теряются — **осознанное ограничение MVP**, не прикручивай БД/Redis.
- Реконнект-токены и слоты игроков — в том же in-memory состоянии комнаты.
- **Все мутации состояния одной комнаты сериализуются** — intent'ы одной комнаты обрабатываются строго по одному, чтобы исключить гонки.

### 3.4 Централизованный конфиг правил
Все константы — в одном модуле `/shared` (например `rules.config.ts`), **никаких магических чисел в логике**:
- костей на старте: 5
- игроков: min 2, max 12
- тихая фаза хода: 0–15 000 мс
- звуковая («жёлтая») фаза хода: 15 000–25 000 мс
- основной таймер хода: 25 000 мс, после чего тратится банк
- личный банк экстра-времени: 30 000 мс (фиксировано, без регенерации в MVP)
- бонус-таймер special round: 7 000 мс
- жест тряски: макс 5 000 мс; порог неподвижности для фиксации: 500 мс
- окно ожидания реконнекта: 60 000 мс
- (структура граней костей — отдельный конфиг, 8.2)

### 3.5 Расширяемость — закладываем СЕЙЧАС
Проект прирастёт ботами, 3D-костями, аватарами (раздел 13). Структурные решения принимаем с их учётом уже сейчас:
- **`GameEngine` управляется абстрактным источником намерений, а не сокетом.** Человек за Socket.io и будущий бот — разные источники одного интерфейса intent'ов. Не завязывай применение хода на наличие сокет-соединения.
- **Рендер костей подменяем** (config-driven, 2D сейчас → потенциально 3D позже).
- **Модель игрока оставляет место под аватар** (опциональное поле) без ломки схемы, хотя в MVP только ник.

## 4. ИНЖЕНЕРНЫЕ СТАНДАРТЫ (глобально)

### 4.1 Качество кода
- TypeScript **strict** везде. `any` — только с письменным обоснованием в комментарии; по умолчанию запрещён, предпочитай `unknown` + сужение.
- У всех функций — явные типы возврата.
- Ориентир **≤ 50 строк на функцию**; длиннее — декомпозируй.
- ESLint + Prettier единым конфигом на монорепо, с первого коммита. В конце фазы код проходит линт без ошибок.
- Именование: булевы — `is`/`should`/`has`; обработчики событий — `handle` (`handleBidSubmit`). Типы — PascalCase.
- Без закомментированного кода и `console.log`-мусора в финале фазы.

### 4.2 Контракт ошибок
- Невалидный intent **никогда не роняет сервер**. Ответ — структурированное событие-ошибка (код + сообщение), состояние не мутирует.
- Единый тип ошибки в `/shared` + коды: `NOT_YOUR_TURN`, `ILLEGAL_BID`, `WRONG_PHASE`, `ROOM_FULL`, `INVALID_TOKEN` и т.п.

### 4.3 Тестирование (дифференцированно)
- Инфраструктура тестов настраивается в Фазе 1: Vitest (client) / Jest (server + shared).
- **Доменная логика (`GameEngine`, чистые функции `/shared`) покрывается содержательными юнит-тестами** — самая ошибкоопасная часть. Особое внимание — валидатору ставок с конверсией единиц (5.4): все переходы + пограничные случаи из worked-примеров.
- UI-тесты в MVP — по минимуму.
- Тесты доменной логики **детерминированы**: RNG инъектируется (6.4), время управляемое.
- **Саму случайную генерацию костей НЕ тестируем** (нет смысла тестировать распределение RNG); тестируем логику, работающую поверх заданных значений костей.

### 4.4 Definition of Done фазы
Собирается; линт и typechecker чисты; тесты своего уровня зелёные; закоммичено; в «Статусе фаз» записано что сделано; критерий готовности фазы выполнен.

### 4.5 Честность/античит уровня MVP
- **Сервер отправляет каждому игроку только его собственные кости** до вскрытия. Чужие кости не покидают сервер, пока раунд не раскрыт. Это корректность, не полиш.
- Реконнект-токен достаточно случаен (не угадываем).
- Таймеры авторитетны на сервере (6.5).

## 5. ПРАВИЛА ИГРЫ

### 5.1 Подготовка к партии
- Игрок создаёт/входит в комнату по коду или ссылке, вводит ник (анонимная сессия, без регистрации).
- Аватарки в MVP не входят — только текстовый ник (модель расширяема под аватар, 3.5).
- Лобби: список подключённых, каждый жмёт «Готов». Партия стартует, когда все готовы.

### 5.2 Стартовый раунд (кто ходит первым)
- Каждый **открыто** бросает 1 кость (с таймером на бросок).
- Наибольшее значение — ходит первым. При равенстве — переброс среди равных.
- Остальные ждут.

### 5.3 Игровой раунд
- У каждого игрока 5 костей (число уменьшается по мере проигрышей).
- Кости бросаются в закрытую; игрок видит только свои и не пересматривает до конца раунда.
- Кости генерируются **на сервере** в момент завершения жеста «тряски» на клиенте (клиент лишь инициирует запрос).
- Игроки по кругу называют ставки «количество + номинал»; ставка относится к **сумме костей ВСЕХ игроков за столом**.
- Ставка обязана **монотонно расти** по единой шкале (5.4). Откат/дубль запрещён.
- Каждый следующий игрок либо повышает ставку, либо говорит «не верю».
- **Первая ставка раунда** может быть на любой номинал, включая единицы, без ограничений; **минимальная — количество 1** **[ДЕФОЛТ — подтвердить]**.
- При «не верю» — все вскрывают кости, считается фактическое количество против последней ставки (с джокерами, 5.4).
- Если фактическое **≥** заявленного — проигрывает сказавший «не верю». Если **меньше** — проигрывает сделавший ставку. (Точное совпадение → проигрывает сказавший «не верю»; спец-бонуса за «точно в цель» НЕТ.)
- Проигравший теряет одну кость. Он же ходит первым в следующем раунде; если уже выбыл (0 костей) — первым ходит следующий по очереди после него.

### 5.4 Единицы (джокер) и шкала конверсии — ТОЧНАЯ ФОРМУЛА
Единицы по умолчанию — джокер (wild): при подсчёте считаются как любой заявленный номинал. Ставки на разные номиналы сравниваются по единой монотонной шкале. Валидатор — чистая функция в `/shared`, обязательно покрыт тестами по всем пунктам ниже.

**Направление «обычный номинал → единицы»:**
- количество единиц = `ceil(количество_обычных / 2)`.
- Пример: 4 пятёрки → 2 единицы (4/2 = 2).

**Направление «единицы → обычный номинал»:**
- базовое количество обычного номинала = `количество_единиц × 2` (БЕЗ «плюс 1»). Это применяется ко ВСЕМ номиналам одинаково, включая шестёрки.
- при этом ставка обязана быть **строго легальным повышением** относительно всего, что уже ставилось (монотонность), — нельзя воспроизвести уже звучавшую ставку.
- **Условное правило шестёрок (только при коллизии).** Шесть — старший номинал, «расти по номиналу» некуда. Поэтому: если базовое `количество_единиц × 2` для шестёрок даёт ставку, которая **уже звучала** (нелегальный повтор), — и только в этом случае — применяется `(количество_единиц + 1) × 2`, чтобы перепрыгнуть на следующий доступный уровень. Если базовое `×2` шестёрок ещё не звучало и легально — берём его как есть, без всякого +1.

**Worked-примеры (это авторитетные тест-кейсы, реализация обязана им соответствовать):**
1. Было `4 четвёрки` → `2 единицы` → игрок хочет пятёрки → `2×2 = 4 пятёрки` — **легально** (номинал 5 старше 4, количество 4 проходит).
2. Было `3 шестёрки` → `2 единицы` → игрок хочет шестёрки → базовое `2×2 = 4 шестёрки`. Четыре шестёрки ещё не звучало ⇒ берём **4 шестёрки**, условное правило НЕ активируется.
3. Было `4 шестёрки` → `2 единицы` → игрок хочет шестёрки → базовое `2×2 = 4 шестёрки` уже звучало ⇒ активируется правило шестёрок `(2+1)×2 = 6 шестёрок`.
4. Было `4 пятёрки` → `2 единицы` → «4 чего-то ниже шестёрки» **запрещено** (перекрыто четырьмя пятёрками); на шестёрки — базовое `4 шестёрки`, если не звучало.

**Важно для реализации:** легальность зависит не только от последней ставки, но и от того, с какого обычного номинала произошёл переход на единицы (см. пример 3). Поэтому валидатор/состояние должны учитывать историю ставок раунда достаточно, чтобы корректно обрабатывать возврат с единиц (как минимум — номинал/количество обычной ставки, предшествовавшей переходу на единицы). Клиент держит ту же историю для предвалидации (5.8).

### 5.5 Special round (аналог Palafico)
- Доступен **любому** игроку с ровно 1 костью (одновременно таких может быть несколько).
- Объявить можно **только до первой ставки раунда**; после первой ставки окно закрыто до следующего раунда.
- Если объявлено во время таймера первой ставки — первому игроку раунда добавляется бонус-таймер **7 сек**.
- Если объявлено хоть кем-то — правило действует **весь текущий раунд для всех**: единицы перестают быть джокером, номинал ставки менять нельзя (только повышать количество).
- В следующем раунде не сохраняется — объявлять заново.

### 5.6 Таймеры хода и звук
Последовательность для игрока, чей ход:
1. **0–15 сек** — тихо, игрок думает.
2. **15–25 сек** — **звуковой сигнал** (пиканье), «жёлтая зона», предупреждение что время на исходе.
3. **После 25 сек** — начинает тратиться **личный банк (30 сек)**.
4. **Банк исчерпан** — срабатывает таймаут-действие (5.7).

Банк тратится только присутствующим (онлайн) игроком как продолжение хода; на дисконнекте банк автоматически не расходуется, но таймер хода идёт (раздел 7).

### 5.7 Таймаут хода и защита от двойной потери
- Когда всё время (25 сек + банк 30 сек) вышло и игрок **не сделал ставку и не сказал «не верю»**: он **теряет одну кость** (как проигрыш раунда), раунд завершается, ход идёт дальше.
- **Защита от двойной потери:** кость по таймауту **не может быть снята два раунда подряд** у одного игрока. Если игрок «завтыкал» (не сделал ставку) второй раунд подряд — на второй раз он кость **НЕ теряет**, ход просто переходит следующему игроку.
- Защита действует **только для чистого завтыка** (ставки не было вообще). Если игрок сделал ставку и проиграл её по «не верю» — кость теряется как обычно, даже два раунда подряд. Иммунитет — исключительно про отсутствие действия, не про честный проигрыш.

### 5.8 UI ставки: подсказки + гибридная валидация
Интерфейс ставки помогает игроку и валидирует ввод в два слоя.

**Подсказки (всегда видны игроку):**
- **Минимально возможная легальная ставка** — доступна в один клик.
- **Переход на единицы** — если сейчас ставка на обычном номинале, показать минимально легальную ставку на единицах (по конверсии 5.4), в один клик. Если переход в данный момент невозможен — кнопка неактивна/подсвечена как недоступная (игрок всегда видит её состояние).
- **Переход с единиц на обычный номинал** — симметрично, если текущая ставка на единицах (с учётом правила шестёрок).
- **Свободный ввод** — игрок сам задаёт количество + номинал.

**Валидация — два слоя, одна и та же функция из `/shared`:**
- **Предпроверка на клиенте, мгновенно.** Клиент импортирует чистую функцию валидации и в реальном времени подсвечивает легально/нелегально ещё до отправки. Для этого клиент держит историю ставок раунда (см. 5.4). Никакого обращения к серверу на каждое движение ввода.
- **Авторитетная проверка на сервере при отправке.** intent уходит на сервер, сервер проверяет ту же функцию заново; при отказе — ошибка `ILLEGAL_BID`. Клиенту не доверяем.

(Real-time валидацию через сокет до отправки не делаем — локальной предпроверки достаточно и она мгновенна; серверная нужна один раз, в момент коммита ставки.)

### 5.9 Условие победы
- Побеждает последний игрок, у которого остались кости.

## 6. ТЕХНИЧЕСКАЯ МОДЕЛЬ ДОМЕНА

### 6.1 Явная машина состояний (обязательно)
Раунд/партию моделируй **явным конечным автоматом**, не россыпью `if`-ов:
```
LOBBY → START_ROLL → ROUND_ROLLING → BIDDING → REVEAL → ROUND_END → (BIDDING следующего раунда | GAME_OVER)
```
- В `BIDDING` есть под-состояние «окно объявления special round открыто» — до первой ставки.
- Каждый intent легален только в определённых состояниях; иначе — `WRONG_PHASE`. Опиши таблицу «состояние × допустимые intent'ы».

### 6.2 Набор intent'ов (всё валидируется на сервере)
`joinRoom`, `setReady`, `rollDice` (тряска), `placeBid`, `callLiar` (не верю), `declareSpecialRound`, `reconnect`. (Голосований нет — см. раздел 7.) Никогда не доверяй клиенту в части чьего это хода и легальности действия.

### 6.3 Изоляция движка
`GameEngine` — класс/модуль без импортов транспорта. Вход: состояние + intent + (инъектированный) RNG. Выход: новое состояние + список событий для рассылки (кому что). Socket.io-слой только транслирует.

### 6.4 Инъектируемый RNG (обязательно)
Генерация костей — за интерфейсом (например `DiceRoller.roll(): number`), реализация подставляется снаружи:
- **В проде — криптографически честный генератор** (`crypto.randomInt` в Node.js): быстрый, статистически ровный, без перекосов наивного `Math.random() % 6`, без «галлюцинаций». **Не использовать LLM/ИИ для генерации костей.**
- **В тестах** — детерминированная/seeded реализация с заданной последовательностью.
- **Никогда не вызывай генератор напрямую в логике** — только через интерфейс, иначе движок нетестируем.

### 6.5 Серверно-авторитетные таймеры
- Отсчёт принадлежит серверу; сервер решает, когда время вышло, и применяет таймаут-действие (5.7).
- Клиент показывает обратный отсчёт и включает звук «жёлтой зоны» как **визуальную/звуковую оценку**, синхронизируемую от сервера; клиент не может продлить своё время.
- Банк тратится явным продолжением хода присутствующего игрока (5.6).

### 6.6 Синхронизация состояния с клиентом
- На каждое изменение сервер шлёт игроку **отфильтрованный снимок** состояния (полный, но чужие кости скрыты до вскрытия). Полный снимок проще и надёжнее диффов для MVP.
- UI **пессимистичный**: действие применяется после подтверждения сервера.

## 7. РЕКОННЕКТ / ОБРЫВ И ЗАВТЫК (голосований НЕТ)

Единая механика и для отключившегося, и для онлайн-игрока, который «завтыкал»:
- Клиент хранит локальный session-токен; при повторном заходе сервер по токену возвращает игрока в тот же слот с тем же состоянием.
- Если игрок (отключён или просто молчит) не действует — работает обычный таймер хода: 25 сек (с «жёлтой зоной» и звуком) + банк 30 сек.
- Время вышло → таймаут-действие (5.7): теряет кость, с защитой от двойной потери подряд при чистом завтыке.
- **Никаких голосований (50%/70% и т.п.) — эта механика полностью убрана.**
- Игрок остаётся частью партии, может вернуться в любой момент; выбывает естественно, когда кончатся кости.

## 8. UI/UX И ГРАФИКА

### 8.1 Инструменты
- Макеты/дизайн-токены — Figma (токены → Tailwind config). 2D-ассеты — Scenario по art bible; готовые промпты в `scenario-prompt-brief.md` (если файл в репозитории). **Агент ассеты не генерирует — только встраивает готовые файлы.**
- Ionic — структура/навигация/интерактив; Tailwind — «пиратская» тема поверх. Angular Material исключён.

### 8.2 Кости
- **2D-иллюстрация** (плоская грань), без 3D и без Three.js/Babylon на клиенте.
- Жест «тряски» — косметическая CSS-анимация; финальный результат приходит с сервера (без псевдоподсказок).
- Грани: состаренные классические точки на текстуре дерева/кости; на «шестёрке» — маленький череп вместо шестой точки.
- **Структура костей конфигурируема** (грани, визуальные значения, правила подсчёта — как данные), рендер подменяем (3.5).

### 8.3 Компоновка стола (2–12 игроков)
- Адаптивная раскладка «вокруг овального стола»: свой игрок всегда внизу по центру (крупнее), остальные по дуге; число мест равно текущему числу игроков (не сетка на 12 с пустышками).
- При 8–12 игроках карточки уменьшаются пропорционально; при нехватке места верхний ряд уходит в горизонтальный скролл, а не сжимается до нечитаемости.

## 9. ДОРОЖНАЯ КАРТА

### Фаза 1 — Скелет монорепо и инфраструктура качества
**Цель:** рабочий каркас и инфраструктура качества, без игровой логики.
**Задачи:** структура `/client /server /shared`; TS strict; ESLint+Prettier единым конфигом; Vitest/Jest настроены; `package.json` в каждом пакете + корневой (dev/build/test/lint); заготовки README.
**Не упусти:** `/shared` собирается и импортируется обоими пакетами; `rules.config.ts` заведён (пусть частично).
**Готово, когда:** `install` + `dev` в client и server поднимаются без ошибок; `test` и `lint` проходят на пустом каркасе.

### Фаза 2 — Доменная логика (`GameEngine`) + тесты
**Цель:** все правила, изолированно и детерминированно, без транспорта и клиента.
**Задачи:** машина состояний (6.1); правила 5.x; чистые функции валидации/сравнения ставок с конверсией единиц (5.4) в `/shared`; инъектируемый RNG (6.4); содержательные тесты, включая **все worked-примеры конверсии (5.4)**, special round, определение проигравшего, таймаут + защиту от двойной потери (5.7), победу партии.
**Не упусти:** движок не импортирует транспорт; RNG не вызывается напрямую; таблица «фаза × intent'ы»; спец-правило шестёрок и зависимость от истории ставок.
**Готово, когда:** `GameEngine` покрыт тестами по ключевым правилам, запускается из теста без сервера; тесты детерминированы и зелёные; worked-примеры 5.4 проходят.

### Фаза 3 — Транспорт + клиент, базовая играбельность
**Цель:** играбельный (некрасивый) сетевой прототип.
**Задачи:** `@WebSocketGateway` поверх `GameEngine`; in-memory комнаты с сериализацией мутаций; отфильтрованные снимки (6.6); клиент Angular 21 + Ionic 9 + Tailwind (Signals-стор, сервисный слой поверх Socket.io); экраны — вход/лобби/готовность, стол (базовая раскладка), ставка с подсказками и клиентской предвалидацией (5.8), вскрытие/итог раунда, победитель; базовый жест тряски → intent.
**Не упусти:** чужие кости не уходят на клиент до вскрытия (4.5); компоненты не трогают Socket.io напрямую; клиентская предвалидация использует ту же функцию из `/shared`; контракт ошибок (4.2).
**Готово, когда:** два браузерных клиента играют полную партию от лобби до победителя.

### Фаза 4 — UI/UX-доводка и графика
**Цель:** встраивание финальной 2D-графики и доводка раскладки.
**Задачи:** встроить ассеты Scenario через конфиг костей; финализировать раскладку стола, UI-рамки, иконки, тему Tailwind по токенам Figma.
**Не упусти:** визуал берётся из конфига, рендер костей подменяем (3.5).
**Готово, когда:** интерфейс соответствует пиратской теме; смена ассетов/темы не требует правок логики компонентов.

### Фаза 5 — Реконнект, таймеры, банк, edge-cases
**Цель:** устойчивость и полные тайминги.
**Задачи:** session-токен и возврат в слот; серверно-авторитетные таймеры (6.5) с фазами 15/25/банк-30 и звуком «жёлтой зоны»; таймаут-действие + защита от двойной потери (5.7); бонус-таймер special round; единая обработка дисконнекта/завтыка без голосований (раздел 7).
**Не упусти:** банк не тратится авто на дисконнекте; таймеры серверные; гонки исключены сериализацией; двойная потеря блокируется только при чистом завтыке.
**Готово, когда:** тестовый сценарий обрыва/молчания корректно приводит к потере кости и её блокировке на второй подряд завтык; возврат игрока по токену работает.

### Фаза 6 — Документация и подготовка к деплою
**Цель:** проект поднимается с нуля по инструкции без доп. вопросов.
**Задачи:** README в каждом пакете + корневой (раздел 11); описать npm-скрипты по смыслу; заготовка деплой-инструкции.
**Не упусти:** деплой-провайдер не выбран (раздел 12) — оставь место под инструкцию, не выдумывай хостинг.
**Готово, когда:** незнакомый с проектом человек поднимает его локально только по README.
